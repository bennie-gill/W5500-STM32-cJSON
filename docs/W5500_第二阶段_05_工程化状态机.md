# W5500 第二阶段 Step 5：工程化状态机（非阻塞、断线重连、Link 处理）

目标：把 UDP/TCP 示例从“跑一次就算”升级到“能长期跑”的工程写法。核心思想与你做串口/RS485 时类似：
- 主循环里跑任务（状态机）
- 不要在初始化里长时间阻塞
- 断线要可恢复（Link Down/Up、对端重启、网络波动）

## 1. 为什么要工程化（常见坑）

- 你把 `while(1)` 写在某个函数里（例如监测 PHY 30 秒阻塞），网络任务就不运行
- TCP 断开后卡在 `SOCK_CLOSE_WAIT`，导致再也连不上
- Link Down 后 socket 不 close，Link Up 后状态机不复位

## 2. 推荐的任务拆分

推荐把网络相关拆成 3 个层次：

- 初始化层：
  - `w5500_init()`（回调注册 + `wizchip_init` + 写 netinfo）
  - `w5500_dump()`（只打印一次）
- 链路层任务：
  - 周期检查 PHY link（每 200~1000ms）
  - Link Down：关闭所有 socket，清状态
  - Link Up：允许业务层重新 open/listen/connect
- 应用层任务：
  - UDP Echo task
  - TCP Server task
  - TCP Client task

## 3. 非阻塞的写法模板

把“每秒打印一次/每秒检测一次”改成“到点再做一次”，而不是 `HAL_Delay(1000)` 卡住：

- 使用 `HAL_GetTick()` 获取毫秒 tick
- 维护 `next_ms`，到点执行一次动作

这样你的主循环可以持续跑多个任务。

## 4. Link Down/Up 处理策略（推荐）

当你检测到：
- Link 从 1 → 0：
  - 对所有使用的 socket 执行 `close(sn)`
  - 记录当前 link=0
- Link 从 0 → 1：
  - 记录当前 link=1
  - 业务层任务会在看到 `SOCK_CLOSED` 时自动 `socket()` 并进入 UDP/TCP 的正常流程

好处：
- 逻辑清晰，不需要在 link up 时强行 connect/listen

## 5. TCP 重连策略（Client 必备）

不要在每次循环都 `connect()`，否则会导致：
- 大量 SYN 重传
- 状态机紊乱

推荐做法：
- 维护一个重连间隔（例如 1s/2s/5s 递增）
- 只有到 `next_retry_ms` 才尝试重新 `connect`

## 6. 超时与重试参数（第二阶段建议知道）

W5500 全局超时：
- `RTR`：超时单位 100us
- `RCR`：重试次数

你可以通过 ioLibrary 设置：
- `wizchip_settimeout(&timeout)`
- `wizchip_gettimeout(&timeout)`

注意：
- 超时设置影响连接建立与发送重试，过大可能导致“卡很久”，过小可能导致“容易断”

## 7. Step 5 验收标准（工程可靠性）

- 拔网线 10 秒插回：UDP/TCP 能恢复（允许重建 socket）
- PC 端关闭再开启 TCP server：板子 TCP client 能自动重连
- 连续运行 30 分钟：不会卡死在某个 socket 状态
